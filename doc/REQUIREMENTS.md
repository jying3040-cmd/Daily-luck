# REQUIREMENTS.md — 需求与业务说明

> 本文回答：这个产品**要做什么**、边界在哪里。
> 实现方式（算法、数据库、加密、API）见 `ARCHITECTURE.md`。

## 1. 项目背景

### 为什么做这个项目

市面上的运势应用普遍存在两个问题：一是靠广告变现，体验被割裂；二是要求用户把生辰八字上传到陌生服务器，隐私无从保障。同时，很多应用的「运势」是每次刷新都变的随机数，连自洽都做不到。

本项目要做一个**反其道而行**的版本：数据只在本机、结果确定可复现、历法依据真实可查。

### 要解决什么问题

| 问题 | 本项目的应对 |
|---|---|
| 生辰八字要上传到别人服务器 | 全部数据存本机 SQLite，敏感字段加密，服务只监听本机回环地址 |
| 运势每次刷新都不一样，感觉被敷衍 | 相同档案 + 相同日期 → 相同结果，并有测试锁定行为 |
| 历法信息是编造的 | 基于 `lunar-typescript` 计算真实的干支历、黄历宜忌与生肖冲煞 |
| 打开就有广告、要注册 | 无账号、无广告、无上报、无追踪 |
| 想了解分数怎么来的 | 算法集中在单一文件，可完整审阅、修改与测试 |

### 目标用户

- **主要用户**：对传统命理与黄历有兴趣、同时在意个人隐私的个人用户。
- **次要用户**：想阅读一个完整 TypeScript 全栈参考项目的开发者。

### 产品定位（重要）

**Daily Luck 是确定性的娱乐产品，不是预测模型。** 界面上的整数分用于呈现相对趋势，不代表统计概率或现实事件发生率。

## 2. 用户角色

| 角色 | 能力 |
|---|---|
| 使用者（单用户） | 全部功能；无账号体系、无权限分级 |

**没有多用户、没有管理员、没有分享与社交功能。** 服务按「单机单用户」设计。

## 3. 功能模块

| 模块 | 需求 |
|---|---|
| 档案管理 | 录入与修改姓名、出生日期、出生时辰、手机尾号、血型与性别；姓名与手机尾号加密保存 |
| 命盘排盘 | 展示八字四柱（年/月/日/时）、星座、生肖、生命数字与日干五行 |
| 五项指数 | 事业、财运、感情、健康、人际五项分类分，附综合分与文字解读 |
| 黄历宜忌 | 幸运色、幸运数字、幸运方位、贵人属相与冲煞生肖 |
| 7 日趋势 | 以今天为中心的前后三天运势曲线 |
| 报告缓存 | 报告按日缓存，重复访问零计算 |

## 4. 核心业务流程

### 首次使用

```text
打开应用
    ↓
填写档案（姓名、出生日期、出生时辰、手机尾号、血型、性别）
    ↓
保存 → 服务端校验 → 加密姓名与手机尾号 → 写入本机数据库
    ↓
展示命盘（八字四柱、星座、生肖、生命数字、日干五行）
    ↓
生成今日报告（五项指数 + 黄历宜忌）
```

### 日常查看

```text
打开应用
    ↓
读取已保存档案 → 计算今日报告
    ↓
命中当日缓存则直接返回（零计算）
    ↓
展示 7 日趋势（今天 ±3 天）
```

### 修改档案

```text
修改字段 → 保存
    ↓
服务端重新校验
    ↓
更新档案 → 重新计算命盘与报告
```

## 5. 业务规则

### 确定性

1. **相同档案 + 相同日期必须得到相同结果。** 这是核心承诺。
2. 运势计算中不得引入真随机或与请求时间相关的因素。
3. 随机波动只能来自「档案与日期的哈希 + 确定性伪随机」，且同一输入下可复现。

### 分数构成

4. 五项分类先由稳定的基础分生成，再叠加以下规则，最后限制到固定区间并平均得到综合分：
   - 历法数据（农历、八字、生肖、宜忌、冲煞、方位）——来自 `lunar-typescript` 与传统规则；
   - 出生日期与时辰 → 四柱、星座、生肖、生命数字与五行关系；
   - 血型、手机尾号、姓名长度 → 对分类分数施加**小幅**加成；
   - 档案与日期的哈希 → 生成稳定的基础分和少量变化。
5. 分数必须落在固定区间内；综合分为五项分类分的平均。
6. 分数只能被表述为「相对高低」，**不得**表述为百分比或准确率。

### 档案与校验

7. 出生日期必须是真实日期，范围为 `1900-01-01` 至今天。
8. 出生时辰格式为 `HH:mm`（`00:00` 至 `23:59`）。
9. 手机尾号最多 4 位数字。
10. 姓名最多 30 字符（超出截断）。
11. 性别只允许 `male` / `female` / `unknown`；血型只允许 `A` / `B` / `AB` / `O` 或空。
12. 所有输入校验失败时返回明确的中文错误提示，且不写入任何数据。

### 报告查询

13. 单次最多查询 **366 天**。
14. `start` 不能晚于 `end`；两者都必须是真实的 `YYYY-MM-DD` 日期。
15. 未保存档案时查询报告返回 `NO_PROFILE`，前端引导用户先填写档案。
16. 报告按「日期 + 波动开关」缓存，重复访问不再计算。

### 数据与隐私

17. 姓名与手机尾号必须**加密后入库**。
18. 服务默认只监听 `127.0.0.1`，不对外开放。
19. 不开放跨域 API 访问。
20. 不进行任何数据上报、遥测或第三方分析。
21. 数据与密钥同时存在于本机；**丢失密钥后加密字段无法恢复**，用户需同时备份数据库与密钥。

### 表述边界

22. 运势与命理内容属于传统文化与娱乐范畴，仅供娱乐参考。
23. 不构成医疗、财务、法律或其他现实决策建议。
24. 免责声明必须在 README 中保留。

### 异常场景

| 场景 | 行为 |
|---|---|
| 未保存档案就查询报告 | 返回 `NO_PROFILE`，前端引导填写档案 |
| 出生日期非法或超出范围 | 400，提示日期范围 |
| 出生时辰格式错误 | 400，提示必须为 `HH:mm` |
| 手机尾号非数字或超 4 位 | 400，提示只能填最多 4 位数字 |
| 查询区间非法（start > end） | 400 |
| 查询超过 366 天 | 400，提示单次最多 366 天 |
| 密钥文件损坏（长度不是 32 字节） | 启动时报错，拒绝以错误密钥运行 |
| 加密值格式损坏 | 解密时抛错，不返回错误数据 |
| 旧库 `daily_reports` 主键结构不同 | 启动时自动迁移到 `(date, jitter)` 主键 |

### 边界与限制

- **单机单用户**：不支持多用户隔离，不提供账号与权限。
- **不联网**：不接入任何外部数据源或模型服务。
- **不保证历法以外的一切**：运势规则是产品自定义的娱乐规则。
- 演示部署（Render 免费层）闲置会休眠，且数据不持久。
- 前端仅中文界面。

### 数据约束

- 数据文件位于项目根目录 `data/fortune.db`；密钥位于 `data/secret.key`（权限 `0600`）。
- 加密字段：姓名、手机尾号。非加密字段：出生日期、出生时辰、性别、血型。
- 报告缓存以「日期 + 波动开关」为主键。

## 8. 验收标准

1. 保存档案后刷新页面，档案与命盘仍正确显示。
2. 同一档案在同一日期多次查询，五项分数与综合分**完全一致**。
3. 姓名与手机尾号在数据库中为密文，无法直接读出明文。
4. 删除 `secret.key` 后，已加密字段无法解密（行为可预期，不静默返回错误数据）。
5. 非法输入（越界日期、错误时辰格式、超长手机尾号）被拒绝并给出中文提示，且不写入数据。
6. 未保存档案时查询报告返回 `NO_PROFILE`。
7. 查询区间超过 366 天被拒绝。
8. 重复访问同一日期报告时命中缓存（不重复计算）。
9. 服务默认只监听 `127.0.0.1`，外部无法访问；跨域请求被拒绝。
10. 前端在桌面与移动宽度下均可正常阅读与操作。
11. `npm run check`（测试 + 构建 + 环境自检）通过；CI 在提交与 PR 上通过。
12. 构建后的生产模式可通过单一端口访问前端与 API。
13. 旧库（`daily_reports` 主键为旧结构）启动后可自动迁移且数据不丢失。
